## 2. Faits établis par les preuves nouvelles

Au second « go » (message 4), l'agent découvre un plan « déjà en v1.1 avec un journal d'exécution rempli » dont les artefacts (voie-l-semantique.py, cache voie L, vetos dans l'arbitre) sont absents du disque hôte — le pattern exact du « journal aspirant » (texte tracé avant action).

**F-2 — Le travail pré-coupure avait été exécuté DANS le dépôt git, pas dans le miroir hôte.** La reprise le découvre explicitement : « le repo révèle une réalité différente : l'exécution pré-coupure a bien eu lieu DANS le repo… le repo équipe ~104 skills, l'hôte seulement 43. Mes “corrections aspirantes” étaient fausses dans leur cadrage ». La convention a été appliquée a posteriori : dépôt = source R4, sync miroir hôte dans cette direction uniquement (règle d'or n°5, v3.26.0 — écrite à la suite de CETTE session).

**F-3 — gen-plan vit « par design » côté dépôt git.** Le dernier message de la discussion l'établit : « gen-plan n'existe que dans le dépôt KNOWLEDGE-repo/skills/ — il est absent du miroir /home/z/my-project/skills/ (104 skills). **F-4 — Le dépôt GitHub porte une lignée gen-plan PLUS AVANCÉE que l'installation locale.** Historique vérifié sur le clone à `e6a9595` : v3.24.0 « parallélisation par défaut » (commit `e9a68a1`, Tasks 25ter→27-B), v3.25.0 « re-matérialisation structure hiérarchique du mode step » (`da549af`, Task B2), v3.26.0 « leçons de la vérité source PM INSTALL » (`b38e0f7` : philosophie #4, règle d'or n°5 anti-aspirant, clause dégradation gracieuse 429). ## 3. Causes racines (RC1-RC4) et leurs mécanismes

**RC1 — Collision de lignée (cause structurante).** Deux gen-plan « v3.24.0 » indépendants coexistent : la lignée canonique du dépôt (parallélisation) et le fork local (E7-DISP). Mécanisme du bug : l'installation du sandbox était épinglée sur un commit ANTÉRIEUR (b75a6206 → v3.23.1) à la lignée publiée (v3.24.0→v3.26.0) ; le correctif local a été développé sur cette base obsolète et a réutilisé un numéro de version déjà consommé. Conséquence : toute référence à « gen-plan v3.24.0 » est ambiguë (KB, PM, journaux, évals), et les leçons anti-bug de la lignée canonique (règle d'or n°5, clause 429, §5.5) manquent à l'instance locale — le correctif E7-DISP traite le symptôme d'affichage mais pas les causes d'aspiration documentées dans la discussion.

**RC2 — Double emplacement (dépôt canon vs miroir hôte).** Conformément à F-3, gen-plan « vit » côté dépôt ; mais le sandbox courant en héberge une instance au miroir `skills/gen-plan/` (installée par PM-INSTALL). Selon la session et le chemin de chargement, deux instances divergentes peuvent être exécutées. C'est le mécanisme exact observé dans s/64c90144 (F-2) : un plan « rempli » côté hôte dont les artefacts vivaient côté dépôt. Pour le bug « plan d'actions non fait/non affiché », le mécanisme symétrique s'applique : une session qui charge l'instance sans le hook E7-DISP (ou sans l'E1-RES étendu) ne finalise pas le protocole — et rien ne le détectait avant l'arbitre.

**RC3 — Reprise post-coupure incomplète.** Le hook E1-RES (étendu en v3.24.0 locale à « tout message pendant un plan en vol ») n'est efficace que si l'instance chargée le porte (RC1/RC2) et si l'état « plan en vol » est dérivable du disque. Dans s/64c90144, la reprise a bien audité le journal pré-existant — mais le lien plan↔dépôt↔miroir n'était outillé nulle part (aucun arbitre), d'où l'erreur de cadrage initiale (« corrections aspirantes » fausses, corrigées ensuite). Leçon : la reprise doit dériver l'état de MÉCANISMES (arbitre P1-P5, convention dépôt=source R4), pas de la mémoire de session.

**RC4 — Interruption plateforme (cause de l'occurrence courante, sans interruption utilisateur).** Dans le présent sandbox, le protocole de génération du plan (Task 21) a été coupé par une erreur d'outil (« context canceled ») APRÈS l'écriture disque (plan + worklog + arbitre survivants, vérifiés à la reprise) mais AVANT l'affichage au chat — le dernier maillon de la chaîne E7→E8→R5→affichage est aussi le plus vulnérable, et il n'était PAS REJOUABLE : l'entrée worklog portait déjà le marqueur PLAN-AFFICHE (écrit avant la coupure) alors que l'affichage n'avait jamais eu lieu. Le propriétaire n'a donc vu aucun plan — 3e occurrence, cette fois sans interruption utilisateur, invalidant l'hypothèse unique « interruption mi-plan » de l'audit Task 15. Contre-mesure v3.27.0 : **l'affichage est REJOUABLE** — à toute reprise (E1-RES), si le plan est protocolairement PASS mais que l'affichage n'est pas prouvé pour la session courante, le bloc récapitulatif est re-affiché AVANT toute autre action (appliqué en direct dans ce tour).

## 4. Qualification de l'hypothèse antérieure

L'audit Task 15 classait la cause racine comme « interruption mi-plan (habitude du propriétaire), aucun garde mécanique sur la chaîne E7→E8→R5→affichage ». Les preuves nouvelles conduisent à la révision suivante : l'absence de garde mécanique reste VRAIE et a été fermée par l'arbitre P1-P5 ; mais l'hypothèse du DÉCLENCHEUR unique (interruption utilisateur) est invalide — les occurrences couvrent au moins trois déclencheurs distincts : interruption utilisateur (occurrence 1), coupure de contexte pendant une exécution côté dépôt/miroir (discussion s/64c90144), interruption plateforme « context canceled » (occurrence courante). Un protocole anti-bug robuste doit donc être invariant au DÉCLENCHEUR : c'est le design retenu pour la reconstruction v3.27.0 (G16).

## 5. Décision de reconstruction et contre-mesures v3.27.0

La reconstruction est **nécessaire** (demande du propriétaire « s'il le faut » — oui) et prend la forme d'une FUSION des lignées, pas d'une régression : **base canonique = dépôt v3.26.0** (source R4 à `e6a9595` — la plus avancée, porte la règle d'or n°5, la philosophie #4, le §5.5 step, la clause 429) **+ report des apports valides du fork local** (hook E7-DISP et son arbitre `check_plan_protocol.py`, extension E1-RES, évals 13 cas, garde anti-verdict-périmé) **→ v3.27.0** (bump MINOR, collision v3.24.0 documentée au journal du SKILL). Contre-mesures intégrées : (1) unification des instances — le miroir hôte est re-projeté byte-identique depuis le dépôt (convention R4, fin de la divergence RC2) ; (2) arbitre P1-P5 présent DANS l'instance canonique (le garde voyage avec le skill) ; (3) affichage rejouable à toute reprise (RC4) ; (4) collision documentée pour empêcher toute réutilisation ambiguë de numéro (RC1). Publication vers GitHub : commit local posé, push au GO du propriétaire avec jeton éphémère (règle d'or n°4 — anti-persistance).
