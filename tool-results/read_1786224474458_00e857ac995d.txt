    17→
    18→# gen-plan v3.3.0
    19→
    20→Skill d'orchestration et de planification structuree pour taches complexes multi-etapes.
    21→Version 3.3.0 : protocole 15 etapes avec decomposition precoce (etape 2),
    22→etape d'invocation gen-plan (etape 3), orchestration d'agents performance-driven,
    23→lecture bloc par bloc (E4), paradigme CoT+Chaining avec auto-correction,
    24→gestion des tokens pour conversations longues, **registre de skills personnalise
    25→avec protocole de decouverte dynamique des skills externes (knowledge base)**.
    26→
    27→## Declencheurs
    28→
    29→- `gen-plan:` suivi d'une description de tache
    30→- `gen-plan:correct-work(projet)` -- verification et correction d'un projet complet
    31→- `gen-plan:correct-work(<cible>)` -- verification/correction d'un element specifique
    32→- `plan d'actions` -- demande explicite de planification
    33→- `orchestre` -- orchestration multi-agents
    34→- Toute demande impliquant plusieurs etapes sequentielles avec des livrables
    35→- `gen-plan:generate(<description>)` -- generation d'un plan auto-executable
    36→
    37→## Modes
    38→
    39→| Mode | Declencheur | Comportement |
    40→|------|-------------|--------------|
    41→| **TACHE** | `gen-plan: <description>` | Planifie et execute une tache specifique |
    42→| **PROJET** | `gen-plan:correct-work(projet)` | Analyse complete du projet, corrections, mise a jour prompt-master |
    43→| **CIBLE** | `gen-plan:correct-work(<cible>)` | Verification/correction d'un element specifique |
    44→| **GENERATE** | `gen-plan:generate(<description>)` | Genere un plan d'actions structure sans l'executer |
    45→
    46→## Philosophie
    47→
    48→1. **Read before planning** -- Toujours lire le projet avant de planifier. Un plan sans
    49→   connaissance du projet est generique et probablement inadequat. La lecture exhaustive
    50→   est un investissement necessaire.
    51→2. **Performance-driven selection** -- Le choix entre skill, agent specialise ou agent
    52→   general est dicte par le gain de performance, pas par une hierarchie rigide.
    53→   Evaluer quelle combinaison produit le meilleur resultat en moins de temps pour chaque
    54→   sous-tache. Un skill avec un protocole pertinent bat toujours un agent nu ; un agent
    55→   specialise bat toujours le general-purpose -- MAIS un skill peut aussi deleguer a un
    56→   agent specialise en interne si cette combinaison produit de meilleurs resultats.
    57→3. **Skills can launch specialized agents** -- Les skills ne sont pas des terminaisons
    58→   mais des orchestrateurs. Un skill charge peut lancer en interne un agent specialise
    59→   (full-stack-developer, ppt-expert, frontend-styling-expert, etc.) quand la sous-tache
    60→   le requiert. Cela cree un modele a deux couches : **Skill (protocole + connaissances
    61→   domaine) -> Agent Specialise (execution)**. Le skill fournit le "comment" (protocole,
    62→   templates, criteres de qualite) ; l'agent fournit le "qui" (capacites specialisees,
    63→   outils, vitesse).
    64→4. **Serial execution by DEFAULT** -- Toutes les taches s'executent UNE A LA UNE dans
    65→   l'ordre defini. Le parallelisme est INTERDIT sauf demande explicite de l'utilisateur
    66→   ET preuve que les sous-taches sont independantes (pas de fichiers partages, pas de
    67→   dependance causale).
    68→5. **Visible progress** -- L'utilisateur sait toujours quelle phase est en cours, ce qui
    69→   est termine, et ce qui vient ensuite.
    70→6. **CoT + Chaining avec auto-correction** -- Chaque etape est executee avec un
    71→   raisonnement structure (Chain-of-Thought) avant l'action. Le chainage des etapes
    72→   suit un pipeline hierarchique ou chaque sortie est verifiee et corrigee avant de
    73→   passer a la suivante. En cas d'echec, le systeme propose une strategie alternative
    74→   avant de demander a l'utilisateur. Inspire du SUPER-AGENT HYBRIDE CoT + CHAINING_v2.
    75→7. **Lecture bloc par bloc** -- Les fichiers volumineux (> 500 lignes) sont lus par
    76→   blocs successifs avec une synthese intermediaire a chaque bloc, evitant la surcharge
    77→   de contexte et garantissant une couverture totale.

    79→## Registre de Skills Personnalise (Knowledge Base)
    80→
    81→### Concept
    82→
    83→En plus des skills natifs de l'ecosysteme z.ai, gen-plan peut utiliser des skills
    84→personnalises stockes dans une **knowledge base externe**. Cela permet a
    85→l'utilisateur d'etendre les capacites de planification avec ses propres skills,
    86→agents specialises et protocoles maison.
    87→
    88→### Declaration du Registre
    89→
    90→Le registre est declare dans la section "Registre KB" ci-dessous. Chaque entree
    91→specifie :
    92→
    93→- **Chemin KB** : Emplacement de la knowledge base sur la machine locale
    94→- **Chemin z.ai** : Emplacement equivalent dans l'environnement z.ai (si applicable)
    95→- **Scan depth** : Profondeur de scan pour la decouverte des skills
    96→
    97→### Registre KB (configurable)
    98→
    99→| Parametre | Valeur |
   100→|-----------|--------|
   101→| **Chemin KB (Windows)** | `C:\Users\PC\Downloads\knowledge\skills` |
   102→| **Chemin z.ai (Linux)** | `/home/z/my-project/skills/` |
   103→| **Scan depth** | 2 niveaux (racine + 1 sous-dossier) |
   104→| **Fichier detect** | `SKILL.md` ou tout `.md` avec YAML frontmatter (name, description) |
   105→| **Priorite** | Les skills KB sont evalues APRES les skills ecosysteme z.ai |
   106→| **Overlap** | Si un skill KB a le meme nom qu'un skill ecosysteme, le skill **ecosysteme**
   107→  est prioritaire sauf si l'utilisateur specifie explicitement le skill KB |
   108→
   109→**NOTE** : Le "Chemin z.ai (Linux)" pointe vers le repertoire ecosysteme natif.
   110→Lors du scan KB, gen-plan detectera les skills ecosysteme ET les skills utilisateur
   111→dans le meme repertoire. Pour distinguer les skills KB des skills ecosysteme,
   112→gen-plan maintient une liste interne des skills ecosysteme natifs (ceux presents
   113→avant le scan KB). Tout skill trouve qui n'est pas dans cette liste interne est
   114→considere comme un skill KB. Si l'utilisateur souhaite separer physiquement ses
   115→skills KB des skills ecosysteme, il peut utiliser un sous-repertoire dedie
   116→(ex : `/home/z/my-project/skills-kb/`) et mettre a jour le "Chemin z.ai" en
   117→consequence.
   118→
   119→### Protocole de Decouverte de Skills (Knowledge Base)
   120→
   121→Ce protocole definit comment gen-plan decouvre et evalue les skills de la
   122→knowledge base externe.
   123→
   124→**Etapes de decouverte** :
   125→
   126→1. **Scanner le repertoire KB** : Lister tous les sous-repertoires contenant un
   127→   fichier `SKILL.md` ou un fichier `.md` avec un YAML frontmatter valide.
   128→2. **Construire la liste de reference (skills ecosysteme natifs)** : Avant le scan,
   129→   lister les skills deja presents dans le repertoire cible. Ces skills constituent
   130→   la "baseline" ecosysteme. Tout skill detecte lors du scan qui figure dans cette
   131→   baseline est tague "Ecosysteme". Les autres sont tagues "KB".
   132→3. **Extraire les metadonnees** : Pour chaque skill detecte, lire le frontmatter
   133→   YAML pour extraire : `name`, `version`, `description`, `requires` (dependances
   134→   inter-skills).
   135→4. **Classifier le skill** :
   136→   - **Skill executable** : Possede un protocole complet (declencheurs, etapes,
   137→     checklist) -- peut etre utilise directement.
   138→   - **Skill de reference** : Document de reference, template, configuration --
   139→     consulte mais pas execute comme un protocole.
   140→   - **Agent specialise KB** : Skill definissant un agent avec des capacites
   141→     specifiques (prompt, outils, contraintes).
   142→5. **Construire le registre dynamique** : Fusionner les skills KB avec les skills
   143→   ecosysteme dans une liste unifiee, ordonnee par pertinence. Chaque skill est
   144→   tague "Ecosysteme" ou "KB" selon la baseline construite a l'etape 2.
   145→6. **Evaluer la compatibilite** : Verifier que les dependances inter-skills
   146→   sont satisfaites (ex : correct-work requiert gen-plan >=3.1.0).
   147→7. **Presenter a l'utilisateur** : Afficher la liste des skills KB detectes et
   148→   leur classification avant de proceder.
   149→
   150→**Format du registre dynamique en sortie** :
   151→
   152→```
   153→## Skills KB Detectes
   154→| Skill | Version | Type | Chemin KB | Compatibilite |
   155→|-------|---------|------|-----------|---------------|
   156→| gen-plan | 3.3.0 | Executable | /skills/gen-plan/ | OK |
   157→| correct-work | 2.2.0 | Executable | /skills/correct-work/ | OK (requiert gen-plan >=3.1.0, integre Registre KB v3.3.0) |
   158→| [custom-skill] | x.x.x | Executable/Ref/Agent | /skills/[custom]/ | OK/N/A |
   159→
   160→## Skills Ecosysteme z.ai (references)
   161→[liste des skills ecosysteme pertinents pour le projet]
   162→```
   163→
   164→**Regle de priorite** :
   165→
   166→1. Si l'utilisateur specifie explicitement un skill KB (`gen-plan: utiliser le skill X de ma KB`),
   167→   le skill KB est prioritaire.
   168→2. Si un skill KB et un skill ecosysteme ont le meme nom, le skill **ecosysteme** est
   169→   prioritaire (sauf override explicite).
   170→3. Si aucun skill ecosysteme ne correspond mais un skill KB correspond, le skill KB est utilise.
   171→4. Les skills KB sont toujours evalues apres les skills ecosysteme dans la matrice de decision.
   172→
   173→**Integrer un skill KB dans le plan** :
   174→
   175→Lorsqu'un skill KB est selectionne pour une sous-tache :
   176→- Charger le `SKILL.md` du skill KB comme reference de protocole.
   177→- Si le skill KB definit un agent specialise, l'utiliser comme executeur.
   178→- Respecter les dependances et versions declarees dans le frontmatter du skill KB.
   179→- Logger l'utilisation du skill KB dans le worklog avec son chemin d'origine.

   183→## Protocole -- 15 Etapes Sequentielles
   184→
   185→Le skill s'execute en suivant les etapes sequentielles ci-dessous. L'ordre est important :
   186→il faut **collecter les demandes, puis decomposer immediatement, puis lire le projet
   187→pour nourrir la decomposition**. La decomposition precoce (etape 2) guide toute l'analyse
   188→subsequente en fournissant une structure cible a verifier.
   189→
   190→**Changement v3.0.0** : L'ancienne "Etape 5 -- Decomposition en Sous-taches" est desormais
   191→en position 2 (apres la collecte des demandes). Une nouvelle "Etape 3 -- Invocation de
   192→gen-plan" decrit le protocole d'appel recursif/chainable sans creer de dependance circulaire.
   193→
   194→### Etape 1 -- Collecte et Analyse des Demandes
   195→
   196→**Objectif** : Relire toute la conversation pour extraire chaque demande explicite et implicite.
   197→
   198→**Checklist** :
   199→
   200→1. Relire tous les messages utilisateur (demandes initiales, specs, contraintes, corrections).
   201→2. Identifier les demandes explicites (ce que l'utilisateur a directement demande).
   202→3. Identifier les demandes implicites (prerequis, effets de bord, consequences logiques).
   203→4. Lister chaque demande sans ambiguite.
   204→
   205→**Methode** :
   206→
   207→- Relire toute la conversation pour extraire chaque demande.
   208→- Si un fichier de travail (`worklog.md`) existe, l'utiliser pour comprendre le contexte.
   209→
   210→### Etape 2 -- Decomposition en Sous-taches
   211→
   212→**Objectif** : Decomposer chaque demande en sous-taches atomiques, avec un ordre logique
   213→d'execution. Cette decomposition initiale guide toute l'analyse subsequente.
   214→
   215→**Pourquoi en position 2 ?** La decomposition precoce oblige a structurer la reflexion
   216→des le depart. L'analyse du projet (etape 4) et l'identification de la nature (etape 5)
   217→viendront ensuite pour affiner, valider ou corriger cette premiere decomposition.
   218→
   219→**Checklist** :
   220→
   221→1. Pour chaque demande identifiee (Etape 1), identifier les sous-taches atomiques necessaires.
   222→2. Ordonner les sous-taches logiquement (prerequis d'abord, puis execution, puis validation).
   223→3. Adapter les sous-taches au type de projet si deja connu :
   224→   - **Projet fullstack** : inclure la verification API frontend-backend, schema BDD, auth.
   225→   - **Projet frontend only** : inclure la verification responsive, accessibilite, composants.
   226→   - **Projet backend/API** : inclure la verification endpoints, validation, securite.
   227→   - **Document/PDF** : inclure la verification contenu, mise en page, coherence des donnees.
   228→   - **Script/automatisation** : inclure la verification edge cases, robustesse, gestion des erreurs.
   229→   - **Auto-deploiement** : inclure la verification securite, integrite, codes retour, nettoyage.
   230→4. Marquer les sous-taches qui necessitent une lecture approfondie du projet pour etre precisees.
   231→
   232→**Methode** :
   233→
   234→- Partir de chaque demande et la decomposer en etapes concretes.
   235→- Verifier que chaque sous-tache est suffisamment precise pour etre executee de maniere autonome.
   236→- **IMPORTANT** : Cette decomposition est **strictement hypothetique** -- elle se base UNIQUEMENT sur la demande de l'utilisateur et le type de projet suppose, SANS lire le code ni les fichiers du projet. Elle ne doit contenir que des suppositions raisonnables.
   237→- Cette decomposition sera **exclusivement** affinee a l'Etape 7, apres que les Etapes 4, 5 et 6 auront fourni les donnees reelles du projet.
   238→
   239→### Etape 3 -- Invocation de gen-plan (Protocole)
   240→
   241→**Objectif** : Definir le protocole d'invocation de gen-plan par d'autres skills ou agents,
   242→sans creer de dependance circulaire. Cette etape decrit COMMENT invoquer gen-plan, elle ne
   243→l'execute pas.
   244→
   245→**Principe** : gen-plan peut etre invoque de deux manieres :
   246→1. **Directement** par l'utilisateur via les declencheurs (voir section "Declencheurs")
   247→2. **Par un autre skill** (ex: correct-work) comme sous-protocole
   248→
   249→**Protocole d'invocation par un skill externe** :
   250→
   251→Quand un skill (ex: correct-work) souhaite invoquer gen-plan, il doit :
   252→
   253→1. **Preparer le contexte** : Rassembler les demandes utilisateur pertinentes dans un format
   254→   structure (liste de demandes avec priorites)
   255→2. **Specifier le mode** : TACHE, PROJET, CIBLE, ou GENERATE
   256→3. **Passer les parametres** :
   257→   - `mode` : le mode d'execution choisi
   258→   - `contexte` : resume du travail deja effectue (si applicable)
   259→   - `cible` : element specifique a verifier (si mode CIBLE)
   260→   - `fichiers_concernes` : liste des fichiers pertinents (si connus)
   261→4. **Lancer gen-plan** : L'agent orchestrateur charge le skill gen-plan et l'execute
   262→   selon son protocole 15 etapes
   263→5. **Recevoir le plan** : gen-plan produit un plan structure (voir "Format de Sortie du Plan")
   264→   que le skill appelant peut utiliser directement
   265→
   266→**Anti-circularite** : Cette etape ne dit PAS "executer gen-plan maintenant". Elle dit
   267→"voici le protocole SI un skill veut invoquer gen-plan". L'execution effective se fait
   268→uniquement quand gen-plan est declenche par l'utilisateur ou par un skill appelant.
   269→
   270→**Exemples d'utilisation** :
   271→- `correct-work` appelle gen-plan en mode PROJET a son Etape 1
   272→- `skill-creator` appelle gen-plan en mode TACHE pour planifier la creation d'un skill
   273→- L'utilisateur ecrit `gen-plan: corriger les bugs du script de deploiement` (mode TACHE)
   274→
   275→### Etape 4 -- Lecture et Analyse du Projet (avec Scan KB)
   276→
   277→**Objectif** : Traverser tous les fichiers du projet pour comprendre structure, architecture,
   278→dependances, etat actuel. **Inclus le scan de la Knowledge Base pour decouverte des
   279→skills personnalises disponibles.**
   280→
   281→**Principe cle** : Un plan sans connaissance du projet est un plan generique et probablement
   282→inadapte. La lecture exhaustive est un investissement necessaire. En position 4, cette lecture
   283→sert a **affiner la decomposition initiale** (Etape 2) avec la connaissance reelle du projet.
   284→
   285→**Checklist** :
   286→
   287→1. **Structure des fichiers** : parcourir l'arborescence, l'organisation des dossiers,
   288→   les fichiers de config (package.json, tsconfig, next.config, tailwind, etc.).
   289→2. **Code source** : lire chaque fichier source significatif (composants, routes, API,
   290→   modeles, utilitaires, scripts) pour comprendre la logique implementee.
   291→3. **Schema de base de donnees** (si applicable) : lire le schema Prisma ou equivalent.
   292→4. **Dependances** : analyser package.json, les imports croises entre modules, les
   293→   dependances externes et leurs versions.
   294→5. **Configuration** : lire les fichiers de config pertinents.
   295→6. **Documentation** : README, worklog.md, specifications, fichiers de reference.
   296→7. **Assets et ressources** : images, templates, fichiers statiques pertinents.
   297→8. **NOUVEAU v3.3.0 -- Scan Knowledge Base** : Scanner le repertoire de la knowledge base
   298→   (chemin declare dans le "Registre KB") pour decouvrir les skills personnalises
   299→   disponibles. Lister les skills detectes, extraire leurs metadonnees (name, version,
   300→   description, type, dependances), et les classer (executable, reference, agent).
   301→   Construire le registre dynamique fusionne (ecosysteme + KB).
   302→
   303→**Methode** :
   304→
   305→- Utiliser les outils de lecture de fichiers (Read, Glob, Grep) pour parcourir chaque
   306→  fichier significatif du projet.
   307→- Ne pas se limiter aux fichiers recemment modifies -- lire tout ce qui est pertinent
   308→  pour comprendre le projet dans son ensemble.
   309→- Si le projet est tres volumineux, prioriser la lecture des fichiers principaux et
   310→  utiliser Grep pour les recherches ciblees.
   311→- **NOUVEAU v3.3.0** : Pour le scan KB :
   312→  - Utiliser Glob pour lister tous les `SKILL.md` ou `*.md` dans le repertoire KB.
   313→  - Pour chaque fichier detecte, lire les 20 premieres lignes pour extraire le YAML
   314→    frontmatter (name, version, description).
   315→  - Classifier le skill selon son contenu (protocole executable vs reference vs agent).
   316→  - Construire la liste fusionnee ecosysteme + KB.
   317→  - Afficher le registre dynamique a l'utilisateur pour validation.
   318→
   319→**Methode de lecture bloc par bloc** (fichiers > 500 lignes) :
   320→
   321→1. Estimer la taille du fichier (nombre de lignes ou de caracteres).
   322→2. Si le fichier depasse 500 lignes, le decouper en blocs de 200-300 lignes.
   323→3. Lire le bloc 1 (lignes 1-300), produire une synthese des findings intermediaires.
   324→4. Lire le bloc 2 (lignes 301-600), produire une synthese et comparer avec le bloc 1.
   325→5. Continuer jusqu'a couverture totale du fichier.
   326→6. Synthetiser l'ensemble des findings intermediaires en un rapport de lecture unifie.
   327→7. Si le fichier depasse 2000 lignes, utiliser Grep pour cibler les sections pertinentes
   328→   avant la lecture bloc par bloc, puis lire uniquement les blocs cibles.
   329→
   330→Cette methode evite la surcharge de contexte tout en garantissant qu'aucune
   331→section pertinente n'est ignoree.
   332→
   333→- **Apres la lecture** : comparer les findings avec la decomposition de l'Etape 2 et
   334→  ajuster si necessaire (sous-taches manquantes, incorrectes, ou superflues).
   335→
   336→### Etape 5 -- Identification de la Nature du Projet
   337→
   338→**Objectif** : Determiner le type de projet, ses technologies, son architecture et sa
   339→complexite. Cette identification conditionne l'ensemble du plan d'actions.
   340→
   341→**Checklist** :
   342→
   343→1. **Type de projet** : application web, API, script, document, analyse, skill,
   344→   auto-deploiement, etc.
   345→2. **Technologies** : framework, langage, base de donnees, outils de build.
   346→3. **Architecture** : monolithe, micro-services, fullstack, frontend only, backend only.
   347→4. **Complexite** : nombre de fichiers, profondeur de l'arborescence, nombre de
   348→   dependances, surface d'interaction.
   349→
   350→**Methode** :
   351→
   352→- Croiser les informations collectees aux etapes 1, 2 et 4 pour determiner la nature du projet.
   353→- La classification n'est pas mutuellement exclusive : un projet peut etre "fullstack + micro-services"
   354→  ou "document + script d'automatisation".
   355→
   356→### Etape 6 -- Identification des Objectifs
   357→
   358→**Objectif** : Lister explicitement chaque objectif a atteindre, sans ambiguite ni omission.
   359→Les objectifs doivent etre specifiques au projet verifie.
   360→
   361→**Checklist** :
   362→
   363→1. Lister chaque objectif derive des demandes de l'utilisateur (Etape 1).
   364→2. Lister les objectifs implicites (prerequis, effets de bord, contraintes).
   365→3. Verifier que chaque objectif est mesurable (on peut dire s'il est atteint ou non).
   366→4. Eliminer les doublons et les redondances.
   367→5. **Croiser avec la decomposition de l'Etape 2** : chaque sous-tache doit correspondre
   368→   a un objectif, et chaque objectif doit etre couvert par au moins une sous-tache.
   369→
   370→**Methode** :
   371→
   372→- Reprendre la liste des demandes (Etape 1) et la transformer en objectifs.
   373→- Valider que chaque objectif est specifique au projet identifie (Etape 5).
   374→- Verifier la coherence avec la decomposition preliminaire (Etape 2).
   375→
   376→### Etape 7 -- Affinement de la Decomposition
   377→
   378→**Objectif** : Affiner la decomposition preliminaire (Etape 2) a la lumiere de l'analyse
   379→du projet (Etape 4), de la nature du projet (Etape 5) et des objectifs (Etape 6).
   380→
   381→**Pourquoi cette etape ?** La decomposition de l'Etape 2 etait faite "a froid" sans connaitre
   382→le projet. Maintenant que le projet est analyse et les objectifs identifies, il faut verifier
   383→et corriger la decomposition.
   384→
   385→**Checklist** :
   386→
   387→1. Comparer la decomposition de l'Etape 2 avec les findings des Etapes 4-6
   388→2. Ajouter les sous-taches manquantes revelees par l'analyse du projet
   389→3. Supprimer les sous-taches superflues ou incorrectes
   390→4. Re-ordonner si necessaire en fonction des dependances decouvertes
   391→5. Verifier que chaque sous-tache est toujours atomique et autonome
   392→
   393→**Methode** :
   394→
   395→- Reprendre la liste de sous-taches de l'Etape 2 comme base
   396→- **IMPORTANT** : Cette etape est le **SEUL endroit autorise** a modifier la decomposition de l'Etape 2. Aucune autre etape ne doit restructurer la liste des sous-taches.
   397→- Chaque modification doit etre **justifiee par un finding specifique** des Etapes 4, 5 ou 6 (ex : "E4 a revele un fichier de config non detecte a E2, ajout de la sous-tache de verification de config").
   398→- La version affinee devient la decomposition de reference pour les etapes suivantes

   400→### Etape 8 -- Detection des Dependances
   401→
   402→**Objectif** : Identifier les dependances entre sous-taches et les contraintes de precedence,
   403→en tenant compte de l'architecture du projet.
   404→
   405→**Checklist** :
   406→
   407→1. Identifier les dependances sequentielles (A doit etre termine avant B).
   408→2. Identifier les dependances paralleles (A et B peuvent etre executees en meme temps).
   409→3. Identifier les dependances conditionnelles (B ne s'execute que si A echoue/reussit).
   410→4. Verifier qu'il n'y a pas de dependances circulaires.
   411→
   412→**Methode** :
   413→
   414→- Construire un graphe de dependances (mental ou ecrit).
   415→- Identifier les chemins critiques (sequence la plus longue de dependances sequentielles).
   416→
   417→### Etape 9 -- Priorisation
   418→
   419→**Objectif** : Classer les sous-taches par priorite en fonction de leur impact sur le
   420→resultat final et de la nature du projet.
   421→
   422→| Priorite | Definition |
   423→|----------|------------|
   424→| **Critique** | Echec invalide le resultat entier |
   425→| **Importante** | Impact significatif sur qualite |
   426→| **Secondaire** | Ameliore resultat mais non bloquant |
   427→
   428→**Methode** :
   429→
   430→- Evaluer l'impact de chaque sous-tache sur le resultat final.
   431→- Prioriser en fonction du type de projet (ex : pour un projet avec BDD, la verification
   432→  du schema est critique ; pour un document, la coherence du contenu est critique).
   433→
   434→### Etape 10 -- Estimation des Risques
   435→
   436→**Objectif** : Pour chaque sous-tache, identifier les risques potentiels et prevoir des
   437→solutions de secours. Les risques doivent etre specifiques au contexte du projet.
   438→
   439→**Checklist** :
   440→
   441→1. **Complexite technique** : la sous-tache requiert-elle des competences ou des
   442→   connaissances specifiques ?
   443→2. **Ambiguite** : la sous-tache est-elle clairement definie ou sujette a interpretation ?
   444→3. **Dependance externe** : la sous-tache depend-elle d'un service, d'une API ou d'un
   445→   outil externe qui pourrait echouer ?
   446→4. **Solution de secours** : que faire si la sous-tache echoue ? Contourner, reporter,
   447→   simplifier ?
   448→
   449→**Methode** :
   450→
   451→- Pour chaque risque identifie, definir une strategie d'attenuation.
   452→- Les risques doivent etre specifiques au contexte du projet (ex : risques de migration
   453→  de schema pour un projet avec BDD, risques de compatibilite navigateur pour un frontend,
   454→  risques de formatage pour un document).

   458→**Objectif** : Produire un plan d'actions formel, complet et adapte au projet.

   461→

   463→   - Nature du projet (type, technologies, architecture)
   464→   - Objectifs principaux
   465→   - Contraintes et hypotheses
   466→
   467→2. **Liste ordonnee des etapes** avec identifiants (1, 2-a, 2-b, 3...) :
   468→   - Pour chaque etape : objectif, fichiers concernes, dependances, priorite
   469→   - Indication du parallelisme possible (etapes independantes executables en parallele)
   470→   - Critere de validation pour chaque etape
   471→   - **Adaptation au projet** : pour chaque etape, indiquer en quoi elle est specifique
   472→     au type de projet verifie et quels points de verification particuliers s'appliquent
   473→
   474→3. **Carte des dependances** : resume des relations entre etapes.
   475→
   476→4. **Matrice des risques** : resume des risques et solutions de secours.
   477→
   478→**Methode** :
   479→
   480→- Structurer le plan selon le format ci-dessus.
   481→- Verifier que le plan couvre tous les objectifs identifies.
   482→- Verifier que l'ordre d'execution respecte les dependances.

   484→### Etape 12 -- Validation du Plan
   485→
   486→**Objectif** : Verifier que le plan est complet, coherent et adapte au projet.
   487→
   488→**Checklist** :
   489→
   490→1. Le plan couvre-t-il toutes les demandes de l'utilisateur ?
   491→2. Y a-t-il des etapes manquantes ?
   492→3. L'ordre d'execution est-il logique (pas de dependance non respectee) ?
   493→4. Le plan est-il adapte au projet (pas de verification generique ignorant les specificites) ?
   494→5. Chaque etape a-t-elle un critere de validation clair ?
   495→6. Les risques principaux sont-ils couverts par des solutions de secours ?
   496→
   497→**Methode** :
   498→
   499→- Relire le plan en entier et verifier chaque point de la checklist.
   500→- Si un probleme est detecte, revenir a l'etape concernee et corriger.

   502→### Etape 13 -- Test et Correction Pre-Integration
   503→
   504→**Objectif** : Tester chaque fichier genere ou modifie AVANT de l'integrer a l'ecosysteme.
   505→
   506→Pour chaque fichier candidat a l'integration :
   507→
   508→1. **Classifier le fichier** :
   509→   - **Skill** : Fichier avec YAML frontmatter (name, description) ou contenu definissant
   510→     un protocole/routine reutilisable
   511→   - **Eco-systeme** : Fichier de configuration, prompt maitre, contexte, memoire, agent,
   512→     ou tout fichier qui etend les capacites du systeme
   513→   - **Utilitaire** : Script, outil, fichier temporaire -- ne pas integrer
   514→
   515→2. **Tester le fichier** :
   516→   - **Skill (.md avec YAML)** : Verifier que le YAML frontmatter est valide (name,
   517→     description presents), que le contenu est coherent et complet (> 200 chars), qu'il
   518→     ne contient pas de fragments ou de placeholders non resolus
   519→   - **Python (.py)** : Compiler avec `compile()` ou `ast.parse()` pour verifier la syntaxe.
   520→     Verifier les imports, les fonctions principales, l'absence de code mort evident
   521→   - **Shell (.sh)** : Verifier le shebang (`#!/bin/bash`), la syntaxe avec `bash -n`,
   522→     l'absence de commandes destructrices non gardees
   523→   - **Markdown (.md)** : Verifier la structure (titres `#`, sections coherentes),
   524→     l'absence de contenu tronque ou de fragments de code incomplets
   525→   - **Configuration (.json, .yaml)** : Valider le format JSON/YAML, verifier les cles
   526→     obligatoires
   527→
   528→3. **Corriger les anomalies detectees** :
   529→   - Si un test echoue, corriger le fichier immediatement
   530→   - Si le fichier est un fragment trop petit (< 100 chars) ou incomplet, le marquer
   531→     comme "invalide" et ne pas l'integrer
   532→   - Si le fichier contient des artefacts de parsing (XML tags, balises `<parameter>`, etc.),
   533→     les nettoyer
   534→   - Documenter chaque correction dans le worklog
   535→
   536→4. **Valider la coherence entre fichiers** :
   537→   - Verifier que les references croisees entre fichiers sont valides
   538→   - Verifier qu'un skill reference dans le prompt-maitre existe bien
   539→   - Verifier qu'un agent mentionne dans la matrice de decision est bien defini
   540→
   541→**Validation de scripts d'auto-deploiement** :
   542→
   543→Pour tout script Python d'auto-deploiement (ex: auto_deploy_*.py), verifier en plus :
   544→- **Securite** : Pas de `shell=True` sans validation, verification des telechargements
   545→- **Integrite** : Verification des magic bytes des fichiers telecharges (MSI: `0xD0CF11E0`)
   546→- **Codes retour** : Verification systematique de `returncode` de subprocess
   547→  (jamais afficher `[SUCCESS]` si le code retour est non-zero)
   548→- **Versions** : Verifier que les versions logicielles referencees existent
   549→  (ex: Node.js 20.18.0 vs 20.18.1)
   550→- **Robustesse** : Gestion des erreurs avec messages clairs en francais
   551→- **Nettoyage** : Verification que les outils installes temporairement sont desinstalles
   552→  en fin de script

   615→
   616→Pour chaque sous-tache, evaluer quelle combinaison produit le meilleur resultat :
   617→
   618→```
   619→1. Existe-t-il un SKILL correspondant ?
   620→   |-- OUI -> Charger le skill
   621→   |   |-- Le skill beneficie-t-il d'un agent specialise ?
   622→   |       |-- OUI -> Skill + Agent Specialise (OPTIMAL)
   623→   |       |-- NON -> Skill seul via agent general (BON)
   624→   |-- NON -> Existe-t-il un agent specialise ?
   625→       |-- OUI -> Agent Specialise seul
   626→       |-- NON -> Agent general (DERNIER RECOURS)
   627→```
   628→
   629→### Criteres de Selection (ordonnes par impact performance)
   630→
   631→1. **Skill + agent specialise** (meilleure performance) -- Un skill dont le protocole
   632→   correspond a la tache ET qui delegue en interne a un agent specialise. Exemple :
   633→   `fullstack-dev` charge, puis delegue a `full-stack-developer`. Le skill fournit
   634→   templates, conventions, criteres de qualite ; l'agent fournit execution specialisee.
   635→2. **Skill seul** (bonne performance) -- Un skill dont le protocole couvre entierement
   636→   la tache sans besoin d'agent specialise. Exemple : `web-search` via `general-purpose`.
   637→3. **Agent specialise seul** (performance moderee) -- Aucun skill correspondant, mais un
   638→   agent specialise (Explore, Plan, frontend-styling-expert, ppt-expert) couvre la tache.
   639→4. **Agent general** (fallback) -- Ni skill ni agent specialise ne convient.
   640→   Ne jamais utiliser comme premier choix -- toujours verifier l'ecosysteme de skills d'abord.
   641→
   642→**Insight cle** : Un skill n'est pas un remplacement pour un agent -- c'est un **accelerateur**.
   643→Charger un skill donne a l'agent des connaissances domaine, des templates et des protocoles
   644→de qualite. L'agent execute plus vite et mieux avec le skill charge que sans lui.

   735→### Gestion des Erreurs et Auto-Correction (CoT + Chaining)
   736→
   737→**Principe CoT+Chaining** : Chaque etape du plan est executee en suivant le cycle
   738→Raisonnement -> Action -> Verification -> Correction (inspire du SUPER-AGENT
   739→HYBRIDE CoT + CHAINING_v2). Ce n'est pas une simple execution lineaire mais un
   740→pipeline intelligent ou chaque sortie est evaluee avant de nourrir l'entree suivante.
   741→
   742→**Cycle d'execution par etape** :
   743→
   744→1. **Raisonnement (CoT)** -- Avant d'executer l'action, expliciter le raisonnement :
   745→   - Quel est l'objectif precis de cette etape ?
   746→   - Quelles sont les contraintes identifiees ?
   747→   - Quelle strategie a ete choisie et pourquoi ?
   748→2. **Action** -- Executer l'etape selon la strategie definie.
   749→3. **Verification** -- Evaluer le resultat produit :
   750→   - Le resultat correspond-il a l'objectif ?
   751→   - Y a-t-il des artefacts, des incoherences, des omissions ?
   752→4. **Auto-correction** -- Si la verification echoue :
   753→   - Corriger le resultat directement si l'anomalie est mineure.
   754→   - Proposer une strategie alternative si l'anomalie est majeure.
   755→   - Documenter la correction dans le worklog.
   756→
   757→**Si une phase echoue apres auto-correction** :
   758→1. Logger l'echec dans worklog avec details erreur + tentative(s) de correction
   759→2. Annoncer l'echec a l'utilisateur avec le diagnostic
   760→3. Proposer des options : retry avec strategie alternative, changer d'agent/skill, ou skip
   761→4. **NE PAS continuer silencieusement** a la phase suivante
   762→5. Si retry, evaluer si un autre type de skill/agent pourrait resoudre le probleme
   763→6. Documenter chaque tentative dans le worklog (cycle CoT complet)

   886→## Regles d'Execution
   887→
   888→- **Serielle par defaut** : Un maximum de taches s'executent en serie, une a la
   889→  fois, dans l'ordre defini. Le parallelisme est INTERDIT sauf demande explicite
   890→  de l'utilisateur ET preuve que les sous-taches sont independantes (pas de fichiers
   891→  partages, pas de dependance causale). L'execution serie maximise la qualite et la
   892→  coherence du resultat global.
   893→- **Quality gates** : Validation apres chaque phase avant de continuer
   894→- **Worklog** : Mettre a jour `/home/z/my-project/worklog.md` apres chaque phase
   895→- **Communications** : L'utilisateur sait toujours ou on en est (progression visible)
   896→- **Tester avant d'integrer** : Aucun fichier n'est integre a l'ecosysteme sans avoir
   897→  passe les tests de l'Etape 13
   898→- **Auto-reapplication** : Si ce skill est mis a jour en cours d'execution, les taches
   899→  restantes sont reevaluees a la lumiere de la nouvelle version (Etape 15)
   900→- **Gestion des tokens** : Si la synthese intermediaire de l'Etape 4 depasse **8000 mots** pour un seul bloc, activer le mode lecture bloc par bloc (decouper en blocs de 200-300 lignes, synthetiser chaque bloc en **500 mots maximum**). Si la conversation est si longue que le contexte risque d'etre sature avant la fin de l'execution, hierarchiser les syntheses : synthese par section, puis synthese des syntheses. Prioriser la qualite sur l'exhaustivite quand le contexte est contraint.
   901→- **CoT+Chaining** : Chaque etape suit le cycle Raisonnement -> Action ->
   902→  Verification -> Correction (voir section Gestion des Erreurs et Auto-Correction).

   926→## Metriques de Qualite du Plan
   927→
   928→Un plan genere par ce skill est evalue selon les metriques suivantes. Ces metriques aident a juger de la qualite objective du plan, au-dela de l'evaluation subjective.
   929→
   930→| Metrique | Definition | Seuil acceptable |
   931→|----------|------------|------------------|
   932→| Taux de couverture | Nombre de demandes utilisateur couvertes par au moins une sous-tache / Nombre total de demandes | 100% |
   933→| Phases avec critere de validation | Nombre de phases ayant un critere de validation explicite / Nombre total de phases | >= 80% |
   934→| Correspondance nature du projet | Nombre de points de verification adaptes au type de projet / Nombre total de phases | >= 60% |
   935→| Couverture des risques | Nombre de phases avec un risque identifie et une solution de secours / Nombre total de phases | >= 50% |
   936→| Dependances respectees | Toute phase qui depend d'une autre est listee apres sa dependance | 100% (0 violation) |
   937→
   938→Ces metriques sont verifiees a l'Etape 12 (Validation du Plan). Si un seuil n'est pas atteint, le plan doit etre corrige avant d'etre presente a l'utilisateur.

   942→## Limites Connues
   943→
   944→Ce skill a les limites suivantes, qu'il est important de connaitre pour l'IA qui l'execute :
   945→
   946→1. **Pas d'execution parallele native** : Le protocole est strictement serie. Le parallelisme n'est possible que si l'utilisateur le demande explicitement et prouve l'independance des sous-taches. gen-plan ne detecte pas automatiquement les opportunites de parallelisme.
   947→
   948→2. **Pas de persistance entre sessions** : Le plan genere n'est pas persiste dans une base de donnees. Si la session est reinitialisee, le plan est perdu. Seul le worklog fournit une trace partielle.
   949→
   950→3. **Pas de verification d'execution reelle** : gen-plan planifie et orchestre, mais il ne verifie pas que le code produit fonctionne reellement (pas de test unitaire, pas de linter, pas de compilation). Cette verification incombe aux skills d'execution (fullstack-dev, coding-agent, etc.) ou a correct-work.
   951→
   952→4. **Dependance a la qualite de la demande** : Si la demande de l'utilisateur est ambigue ou incomplete, le plan reflétera cette ambiguite. gen-plan ne remplace pas une specification formelle.
   953→
   954→5. **Matrice de selection semi-dynamique (v3.3.0)** : La partie ecosysteme du "Guide de Selection Agent/Skill" reste statique. La partie Knowledge Base est dynamique (construite a l'Etape 4). Si de nouveaux skills sont ajoutes a l'ecosysteme natif, la matrice statique doit etre mise a jour manuellement. En revanche, les skills KB sont decouverts automatiquement a chaque execution.
   955→
   956→6. **Accessibilite de la Knowledge Base (v3.3.0)** : Le scan de la knowledge base suppose que les fichiers sont accessibles depuis l'environnement d'execution. Si le chemin KB n'est pas accessible (ex : chemin Windows dans un environnement Linux sans montage), le scan est saute et seuls les skills ecosysteme sont utilises. L'utilisateur est informe du skip.
